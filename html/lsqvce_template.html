lsqvce_template

Starting point for your own least-squares adjustment case.

Syntax

L = lsqvce_template(procOpt)

Description

Copy template/lsqvce_template.m, rename it, and fill in the two stubs at the bottom. It returns the cell array of Loaders the toolbox consumes:

L = myCase(procOpt);
R = lsqvce.engine.adjustVCE(L, procOpt.days, ...
        'verbose', procOpt.loggingLevel, ...
        'logFid',  procOpt.loggingOverviewFileID, ...
        'GroupBy', 'obsType').run();             % constructor-only since 2.0
R.summary();        % what each stream ended up as
R.convergence();    % when the loop settled
This file has two registers. buildLoaders is real, runnable code — it derives one Loader per entry of procOpt.observationGroups. myBuildDay and myEpochCov are stubs that error until you write them. Running the file as shipped therefore gets you Loaders that error on first use; that is the expected state until the stubs are filled. A plausible fake would be worse than an honest stop.

What you write

FunctionReturnsRequired?
myBuildDay.A (m×nc), .B (m×nl), .l (m×1), .t (m×1), optional .arcIdx, .nAxisalways
myEpochCov.Cep (nEpoch×d×d) and .arc(i).epochs/.rowsmulti-axis streams only
myBuildDay must be DETERMINISTIC. The accumulator reads every day a second time for the residual pass and must get identical data back. A random draw or a changing file corrupts the residuals silently, not loudly.
Rows are EPOCH-MAJOR for multi-axis streams, i.e. [x₁ y₁ z₁ | x₂ y₂ z₂ | …]. The temporal correlation model strides by nAxis, so a stream stored axis-major comes out with its time law stretched by the axis count — and it will not announce itself.

procOpt is immutable input, not shared state

procOpt is captured when makeLoader is called and piped through unchanged for the whole run. It must not carry live cursors: a field like iteridx would freeze at its value on the first pass while the loop iterates around it, and your builder would silently read the wrong pass forever. The engine tracks these itself — use ctx.pass and ctx.sysID.

State each value once

Values your pipeline needs before any toolbox object exists stay in your configuration, and the toolbox is fed from them. Never type the same value in both places:

Your fieldFeedsNote
procOpt.daysthe days argumentpositional
procOpt.loggingLevel'verbose'0 silent, 1 progress, 2 detail. 3 is rejected (merged into 2)
procOpt.loggingOverviewFileID'logFid' 
procOpt.showAndSaveGraphicsan if around hook attachmentnot an option
procOpt.observationGroupsobservationTypes + 'GroupBy'a derivation, one Loader per group

nc and nl are derived from the commonParams/localParams row counts. There is no nc argument on adjustVCE (retired R5 M4: Model "vce" is a policy of the joint estimator) or adjustBlock: the common-parameter count is stated once, where the parametrisation is defined.

Merging systems

Two satellites must share one system whenever an observation's design couples both of their local parameters — an inter-satellite range or range-rate does exactly this. The block-arrow model has one local block per system, so a coupling observation cannot span two of them; give both satellites' streams the same group entry and stack their locals. Streams that are merely correlated do not need merging — variance-component estimation handles that.

systemId must be numeric or a single char. The accumulator indexes systems by [store.sysID], which flattens a multi-char string into separate elements. Carry a readable label in 'name' instead.

Optional plot hooks

A hook is a handle you write, @(ctx) -> figureHandle. The engine calls it and owns the show/export/close entirely, so your hook only builds a figure. A hook that throws is logged and skipped — plots never break the solve. postSolve fires after each solve; postModel fires once after the stochastic model is fitted and its ctx additionally carries .psd, .psdFreq, .acv and .arOrder. The template carries a commented stub with the full ctx schema.
