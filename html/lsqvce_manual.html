1 Introduction

lsqvce is a MATLAB toolbox for least-squares adjustment with variance component estimation. You describe your measurements and your unknowns; the toolbox estimates the unknowns, works out how noisy each kind of measurement really is, and tells you whether the result can be trusted.

It was built for satellite gravity recovery (GRACE / GRACE-FO). There, millions of correlated observations from several instruments determine a few thousand common parameters, together with many nuisance parameters per arc or per day. It works just as well on a small problem: a levelling network, a calibration, or a curve fit.

1.1 What it does for you

  • Solves the adjustment. A linear or linearised Gauss–Markov model. The common parameters are shared by all data. The local parameters belong to one arc, one day or one instrument. They are eliminated on the fly, so the full design matrix is never formed and memory stays small.
  • Learns the noise from the data. With Estimate = "noise" the toolbox estimates, for every observation stream, the spectral shape of its noise, its level, and a variance factor per arc. You only have to give a starting guess.
  • Regularises by declaration. A prior (a Kaula rule, minimum constraints, a background model) is a group of pseudo-observations in your own columns. It is treated like data and can have its weight estimated.
  • Judges the result. Global test, outlier tests, redundancy numbers, minimal detectable biases and the whiteness of every stream are reduced to one verdict by R.report.
  • Is robust on request. M-estimation with Huber, IGG3 or bisquare weights, in the same loop as the noise estimation. Nonlinear models are solved by damped Gauss–Newton (the batched kind with x0); robust weights and Gauss–Newton do not combine yet.
  • Lets you watch. A hook runs after every pass, and one plot answers each question afterwards.

1.2 Three lines

lsqvce_setup                                   % once, to install
R = lsqvce.fit(task, Estimate="noise");        % the one verb
R.report                                       % the verdict

task is a lsqvce.TaskDefinition that describes your problem, filled with flat add calls. The options say how to run it. R holds everything that comes back. The toolbox has these user-facing names:

2 Installation

2.1 Requirements

MATLAB R2024a or later. The Parallel Computing Toolbox is optional (Parallel.Mode = "parfor" | "spmd"); without it the toolbox runs serially and says so once per run.

2.2 Install

cd <toolbox root>          % the folder holding +lsqvce
lsqvce_setup               % or lsqvce_setup('install')

Run this once, from the folder that holds +lsqvce. It adds exactly two path entries — the root with the lsqvce.* packages, and examples/ — builds the Help browser index so that doc lsqvce opens this Manual, saves the path, and prints a check report. template/ is not added: you copy a template into your own project.

lsqvce_setup('check')      % version, path entries, doc index, whether lsqvce.fit resolves

3 Key concepts

This chapter introduces the vocabulary the rest of the Manual uses. It has no code to run. Read it once before the tutorial. The words in bold are the names you will meet as method names, options and chapter titles.

3.1 The adjustment in one paragraph

You have observations l that depend on unknown parameters x through a linear (or linearised) model, l + v = A x, where v are the errors. Least squares picks the x that makes the weighted errors smallest. The weights are the inverse of the noise covariance of the observations. Usually you do not know that covariance well. Variance component estimation (VCE) estimates it from the residuals, re-weights, and solves again until the weights settle. lsqvce does all of that in one call, lsqvce.fit.

3.2 Three kinds of problem

Every problem is declared as one lsqvce.TaskDefinition, made in one of three ways:

kind made with use it when
matrices TaskDefinition.fromMatrices(A, l, Weights=p) the whole design matrix fits in memory
batched TaskDefinition.fromBatches(@batchFcn, NumBatches=K, NumUnknowns=u) (or X0=x0) it does not fit, or the model is nonlinear; your function returns one block of rows at a time
streaming TaskDefinition(Days=...) and its add calls the data come per day and per arc, from several instruments, with nuisance parameters and correlated noise

The first two are ordinary least squares with diagnostics. The streaming kind is what the toolbox is built for, and the rest of this chapter describes it.

3.3 Parameters: common and local

Ask of every unknown: over what span is it constant, and who sees it?

  • Common parameters (task.addCommon) are seen by all data, for example the gravity-field coefficients or station coordinates. They are what you want to know.
  • Local parameters (sys.addLocal of a system) belong to one arc, one day or one system, for example an initial orbit state, an accelerometer bias, or a per-arc offset. They are nuisance parameters. The toolbox eliminates them arc by arc while it reads the data, so their number does not cost memory.

You declare both by name and scope: Scope="common", "day", "arc" or "system" says over which span the parameter is constant. A declared name is a template: the toolbox instantiates it once per scope (an "arc" local once per arc) and counts the columns itself. Your code refers to parameters by name; you never compute a column index.

3.4 Data: systems, days, arcs and streams

task = lsqvce.TaskDefinition(Days=1:30)       the calendar
├── addCommon(names)                            what everybody estimates
├── addPrior(name, ...)                         priors on the common parameters
└── addSystem(name, Prepare=@p)                 one per satellite, receiver, instrument group
     ├── Prepare                                (optional) once per day: what its streams share
     ├── addLocal(names, Scope=...)             its nuisance parameters
     ├── addPrior(name, ...)                    priors on its local parameters
     └── addStream(name, Build=@b, Noise=...)   one per observation type  ──►  the streams
          └── Build                             once per day: the rows of this stream
  • A system is one source of data with its own nuisance parameters, for example one satellite, or a satellite pair whose inter-satellite ranging depends on both orbits.
  • A day is the unit of reading. The toolbox asks for the data of one day at a time.
  • An observation type is a kind of measurement within a system, for example "pos" and "kbr". Each addStream declares one; each (system, observation type) pair is one stream, with its own Build function and its own noise law.
  • An arc is one continuous piece of a stream on a day. The noise is correlated within an arc and independent between arcs. Build adds the day’s arcs one by one.

3.5 The two functions you write

You do not hand the toolbox your data. You hand it functions that produce the data on demand. This is what keeps memory small, but it has one consequence: the toolbox calls your functions more than once for the same day, so they must return the same result every time.

Build (one per stream, required) returns the arcs of one day of its stream:

out = build(day, ctx)            % given to addStream(..., Build=@build)
%   out = ctx.newDay();
%   out.addArc(A, l, t, Local={names, P})   once per arc:
%      A  design of the common parameters   (m x nc, columns in addCommon order)
%      l  observed minus computed           (m x 1)
%      t  epochs in seconds                 (m x 1)
%      Local  the partials of local parameters, by name

Prepare (one per system, optional) does the work that every stream of a day shares, once per day, before the first Build of that day. Its result reaches every Build of the day as ctx.Prepared:

P = prepare(day, ctx)            % given to addSystem(..., Prepare=@prepare)

Without Prepare, a system with two streams computes anything they share twice per day: an orbit integration, a large file read, a coordinate rotation. With it, the shared work happens once per build of the day. The tutorial uses it; chapter Declaring your problem shows when it pays.

Both receive the same two arguments: the day and a lsqvce.DayContext, ctx, which carries the names of the system and stream, your Settings, the arc schedule of the day (ctx.ArcIds) and the parameter names, and finds columns by name (ctx.cols).

3.6 What fit does with them

For a run with Estimate = "noise", fit repeats one pass until the noise settles:

for every pass
    for every system and every day
        P = Prepare(day, ctx)                     once per day (if declared)
        for every stream
            out = Build(day, ctx)                 the day's arcs, with ctx.Prepared = P
            whiten every arc with the stream's current noise law
            eliminate the local parameters of the arc
            add the arc to the normal equations of the common parameters
    solve for the common parameters
    read the days again: residuals, redundancies
    update the noise law of every stream, its level, and every arc factor
until no variance component changes by more than Tolerance
diagnose: outlier tests, reliability, whiteness  ->  R.report

With Estimate = "none" (the default) the loop runs once: one solve under the noise you declared. Each day is read at least twice per pass, once to accumulate and once for the residuals. Options.CacheDays decides how many built days are kept in memory between the two reads.

3.7 The noise model

Each stream has a noise law (addStream(..., Noise=lsqvce.Noise.<law>(...))): how its errors correlate from epoch to epoch (the law) and how large they are (its sigma). On top of that, every arc can have its own arc factor, which catches one bad pass without spoiling the whole stream. With Estimate = "noise" the toolbox estimates all of them, as far as the stream’s Estimate setting allows. You start from an honest guess, usually white noise (lsqvce.Noise.white(sigma)) with a realistic sigma.

The result of all weights together is summarised by σ₀ (R.sigma0), the a-posteriori standard deviation of unit weight. A σ₀ near 1 means the declared and the observed noise agree.

3.8 The result and the verdict

fit returns one lsqvce.Results object, R. It holds the estimate R.x, its covariance, the estimated noise model, the per-observation diagnostics, the history of the passes, and a record of how the run was made (R.meta). R.report reads all of this and prints a verdict in five levels:

level question
0 integrity does the arithmetic hold?
1 global are model and noise consistent with the data?
2 localise which observations are suspect?
3 reliability which errors could go undetected?
4 parameters how well is each parameter known?

The verdict is one of PASS, PASS WITH WARNINGS, SUSPECT and INVALID (see Reading the results and the report).

3.9 Glossary

term meaning

4 Your first adjustment

This chapter has two parts. Part 1 fits a straight line in three lines of code. Part 2 builds a small streaming problem from scratch: two instruments, ten arcs, an unknown offset per arc, and noise whose colour is unknown. That is the shape of every real case the toolbox is built for. Part 2 is the file examples/demo_tutorial.m; run it, then read on.

4.1 Part 1 — A straight line

Copy this into the Command Window:

rng(1);
t     = (0:0.1:10).';
A     = [ones(size(t)), t];                 % offset and slope
xTrue = [2; 0.5];
sigma = 0.1;                                % the noise of every observation
l     = A*xTrue + sigma*randn(size(t));     % simulated measurements

task = lsqvce.TaskDefinition.fromMatrices(A, l, Weights=ones(size(t)) / sigma^2);   % WEIGHTS: 1/sigma^2
R = lsqvce.fit(task);
R.report
R.coefficients()

R.report ends in VERDICT: PASS, and R.coefficients() prints

    index    estimate       se        lower      upper
      1       1.9845     0.019632     1.9461      2.023
      2       0.5022     0.003392    0.49555    0.50885

the estimate of offset and slope, its standard error, and a 95 % confidence interval. Both intervals contain the truth (2 and 0.5). R.sigma0 is 0.994: the weights you gave match the scatter of the data.

Two things to remember from part 1:

  • Weights holds weights, 1/σ², not standard deviations.
  • A σ₀ far from 1 means the weights are wrong in scale. Fix that before anything else.

If your problem fits in memory and the noise is known, this is all you need. The rest of the chapter is for data that do not fit this mould.

4.2 Part 2 — A streaming problem

4.2.1 The case

A platform observes a periodic signal of one hour period,

y(t) = a·cos(2πt / 3600) + b·sin(2πt / 3600),

with two instruments on one clock, a gauge and a radar. It records two arcs a day of two hours each (240 epochs, 30 s apart) on five days. Every arc starts with an unknown offset that both instruments see. The gauge has white noise with σ = 0.05. The radar has correlated noise (AR(1), φ = 0.5) with σ = 0.02, but we pretend we do not know that and declare it white.

what here in general
common parameters a, b what you want to know
local parameters one offset per arc (10 in all) nuisance parameters, eliminated
system the platform one satellite, receiver, instrument group
observation types 'gauge', 'radar' the kinds of measurement
what both streams share per day the epochs and the signal basis an orbit, a file, a rotation

4.2.2 Step 1 — Declare the task: its parameters and calendar

task = lsqvce.TaskDefinition(Days=1:5);
names = ["cosAmp" "sinAmp"];
task.addCommon(names);                             % Scope="common" (default)

A task is one object you fill with add calls. addCommon declares the parameters every system sees, by name; Scope="common" means one value for the whole run.

4.2.3 Step 2 — Declare the system: its Prepare, locals and streams

truth = [0.8; -0.3];                               % the simulator's truth
sys = task.addSystem("platform", Prepare=@prepareTutorialDay, Arcs=2, ...   % arcs 1 and 2
                     Settings=struct('epochs', 240, 'step', 30, 'truth', truth));
sys.addLocal("bias", Scope="arc");                 % one offset per arc
sys.addStream("gauge", Build=@buildGauge, Noise=lsqvce.Noise.white(0.05));
sys.addStream("radar", Build=@buildRadar, Noise=lsqvce.Noise.white(0.02));   % colour unknown

Line by line:

  • addSystem declares the platform. Its Prepare function runs once per day, before the streams of that day; whatever it returns reaches every stream as ctx.Prepared.
  • Arcs=2 is the arc schedule: arcs 1 and 2 on every day. A system without "arc" parameters may leave it out (its arcs are then simply the arcs Build adds). With "arc" parameters it is required, because their number must be known before any data is read; leaving it out is an error that says so.
  • Settings is a struct of your own. The toolbox passes it unchanged to your functions as ctx.Settings. Here it carries the simulator’s settings. In a real case it carries a data directory, a model file, a reference frame.
  • addLocal("bias", Scope="arc") asks for one parameter per arc. The toolbox counts them (5 days × 2 arcs = 10) and places them; your code names them.
  • Each addStream is one observation type with its own Build function, which runs once per day of that stream, and its own noise law. lsqvce.Noise.white(0.05) is white noise of standard deviation 0.05.

4.2.4 Step 3 — Write Prepare: what both instruments share

Both streams need the epochs of every arc and the signal basis at those epochs. Computing this in each Build would do it twice per day. Prepare does it once:

function P = prepareTutorialDay(day, ctx)
    cfg  = ctx.Settings;
    nArc = numel(ctx.ArcIds);
    P = struct('t', {cell(1, nArc)}, 'G', {cell(1, nArc)}, 'y', {cell(1, nArc)});
    for a = 1:nArc
        start  = (day - 1) * 86400 + (ctx.ArcIds(a) - 1) * 43200;  % arcs at 0 h and 12 h
        t      = start + (0:cfg.epochs - 1).' * cfg.step;
        w      = 2 * pi / 3600;
        G      = [cos(w * t), sin(w * t)];
        rs     = RandStream('mt19937ar', 'Seed', 100 * day + ctx.ArcIds(a));
        bias   = 0.5 * randn(rs);                      % this arc's true offset
        P.t{a} = t;
        P.G{a} = G;
        P.y{a} = G * cfg.truth + bias;
    end
end

It receives the day and a lsqvce.DayContext, ctx: here its Settings and ArcIds, the arcs of this day. Whatever it returns, P, is handed to every Build of the same day.

4.2.5 Step 4 — Write Build: the rows of one instrument

function out = buildGauge(day, ctx)
    out = instrumentDay(day, ctx, @(rs, m) 0.05 * randn(rs, m, 1));    % white
end

function out = buildRadar(day, ctx)
    phi = 0.5;                                                         % AR(1)
    out = instrumentDay(day, ctx, @(rs, m) arNoise(rs, m, phi, 0.02));
end

function out = instrumentDay(day, ctx, noise)
    P   = ctx.Prepared;                                % prepareTutorialDay's result
    out = ctx.newDay();
    c   = char(ctx.Stream);
    for a = 1:numel(ctx.ArcIds)
        m  = numel(P.t{a});
        rs = RandStream('mt19937ar', 'Seed', 1000 * day + 10 * ctx.ArcIds(a) + double(c(1)));
        out.addArc(P.G{a}, P.y{a} + noise(rs, m), P.t{a}, ...    % A, observed - computed, t [s]
                   Local={"bias", ones(m, 1)});                  % this arc's offset
    end
end

(arNoise draws AR(1) noise of standard deviation 0.02; it is in the example file.) The four rules every Build follows:

  1. One addArc per arc, with the design A of the common parameters (one column per addCommon name, in that order), l and the epochs t, all with the same number of rows.
  2. Local parameters by name, never by column. Local={"bias", ones(m, 1)} gives the partial of the arc’s bias; the toolbox knows which column that is on this day and arc.
  3. Raw rows. l is observed minus computed, unweighted and unwhitened. The toolbox applies the noise law itself.
  4. Deterministic. The toolbox reads every day more than once. Here the random noise comes from a stream seeded on (day, arc, instrument), so every call returns the same rows. Your file reader is deterministic anyway.

4.2.6 Step 5 — A first run under the declared noise

R1 = lsqvce.fit(task);
R1.coefficients()

Estimate = "none" is the default: one solve with the weights you declared. Always run this first. It shows that the declaration is accepted (a declaration mistake is refused by the call that makes it, with its name) and that σ₀ is plausible. Here σ₀ = 0.993.

4.2.7 Step 6 — Estimate the noise

opts = lsqvce.Options(Estimate="noise", Seed=1);
R = lsqvce.fit(task, opts);
R.report

The loop solves, looks at the residuals of every stream, updates each stream’s noise law and arc factors, and solves again. It stops when nothing changes by more than Tolerance; here after four passes (R.stopReason is "converged"). Seed makes the random probes that estimate the redundancies reproducible.

The report ends in VERDICT: PASS. Its Level 1 says “The stochastic model settled in 4 pass(es)” and “Global test PASSES”.

4.2.8 Step 7 — Compare

demo_tutorial prints:

param       truth       declared noise      estimated noise
cosAmp     0.8000     0.8011 +- 0.0005     0.8012 +- 0.0008
sinAmp    -0.3000    -0.3006 +- 0.0005    -0.3004 +- 0.0008
sigma0                           0.993                1.000   (converged)

The estimates hardly move. What moves is how well you know them. In the first run, σ₀ was fine, because the radar’s level was declared right. But its colour was not: correlated errors carry less information than white ones, so the first run’s standard errors are about 1.6 times too small. After the noise estimation they are honest. This is the most common way an adjustment goes wrong without any error message, and the reason Estimate = "noise" exists.

5.2 Step 2 — List the parameters

Declare every parameter by name and scope. addCommon declares the parameters every observation can see (for gravity recovery: the spherical-harmonic coefficients); a system’s addLocal declares the nuisance parameters that live on one arc, one day or the whole system (initial states, accelerometer calibration, empirical terms):

task = lsqvce.TaskDefinition(Days=1:30);
task.addCommon(myCoefficientNames);                    % Scope="common": one value per run
sys = task.addSystem("mission", Settings=struct('dataDir', '/data/mission'), Arcs=4);
sys.addLocal(["bias" "drift"], Scope="arc");           % one each per arc

The toolbox derives every count and every column position from the names and scopes. See Declaring your problem for the scopes, validity intervals and Info columns.

5.3 Step 3 — Declare the streams and their noise

sys.addStream("range", Build=@buildRange, Noise=lsqvce.Noise.white(2e-7));   % white, 2e-7

Each addStream is one observation type: its name, its Build function and its noise law. Start with lsqvce.Noise.white and a realistic level; the estimator can find the colour (Choosing the stochastic model). The system’s Settings (step 2) is a struct of your own that reaches your functions as ctx.Settings.

5.4 Step 4 — Write Build

One function per stream returns the arcs of one day:

function out = buildRange(day, ctx)
    arcs = readMyArcs(ctx.Settings.dataDir, day, "range");   % your reader, deterministic
    out = ctx.newDay();
    for a = 1:numel(arcs)
        m = numel(arcs(a).omc);
        out.addArc(myPartials(arcs(a)), arcs(a).omc, arcs(a).tSeconds, ...   % A, l, t [s]
                   Local={["bias" "drift"], [ones(m, 1), arcs(a).tRel]});    % by name
    end
end

Return raw, unwhitened rows; never scale them by your weights. A has one column per common parameter, in addCommon order; the local partials go by name in Local, and the toolbox places them in this arc’s (or this day’s) columns.

What the context gives you, in plain words:

ctx. what you get

System, Stream the names of the system and the stream
Settings the system’s Settings, unchanged

cols(names) the columns of named parameters, for a local design you build as one matrix B

Build must be deterministic: the toolbox calls it at least twice per day and pass, and must get the same rows back each time.

5.5 Step 5 — Share the expensive work of a day: Prepare

Build is called once per day and stream. If your system has several streams that rest on one expensive computation — an orbit integration with its partials, a large file both streams read, an Earth-rotation matrix for every epoch — that computation would run once per stream. Move it into the system’s Prepare:

sys = task.addSystem("grace", Prepare=@myPrepare, Settings=struct('dataDir', '/data'));
sys.addStream("pos", Build=@buildPos, Noise=lsqvce.Noise.white(0.02), Axes=3);
sys.addStream("kbr", Build=@buildKbr, Noise=lsqvce.Noise.white(1e-7));

function P = myPrepare(day, ctx)
    P.orbit = integrateOrbit(ctx.Settings.dataDir, day);   % the expensive part, once
end

function out = buildKbr(day, ctx)
    out = rangeRateArcs(ctx.Prepared.orbit, ctx);          % what myPrepare returned today
end

What to know:

  • It runs once per build of a day, before the first Build of that day, and its result P reaches every Build of that day as ctx.Prepared.
  • Its context carries the day, the system’s Settings and its scheduled arcs (ctx.ArcIds); ctx.Stream is empty.
  • Settings must not have a field named prepared of its own: that name carries the result (lsqvce:makeLoader:preparedField, reported by fit under its own prefix).
  • Only the current day’s result is kept. A day that is built again (the default CacheDays = 1 builds each day twice per pass) runs Prepare again, so it must be deterministic too. CacheDays = Inf builds every day only once per run, if memory allows.
  • If it throws, the error is lsqvce:makeLoader:prepareDay, naming the day, with your error attached as the cause.

A system with one stream gains nothing from Prepare; leave it out. The tutorial (Your first adjustment) and template/kbr_variational.m use it.

5.6 Step 6 — First run: one solve under the declared model

R = lsqvce.fit(task);          % Estimate = "none"
R.report

Check two things before anything else: that the run completes (a declaration mistake is refused by the add call that makes it, or by fit naming the system and stream), and that R.sigma0 is plausible. A σ₀ far from 1 means the declared accuracies are wrong in scale — fix that before estimating anything on top of it.

5.7 Step 7 — Estimate the stochastic model

opts = lsqvce.Options(Estimate="noise", Pool="stream", Seed=1);
R = lsqvce.fit(task, opts);
R.report
R.plot("psd"); R.plot("convergence");

The loop re-solves until the noise laws settle. Pool decides which streams share one spectral shape; ArcFactors (default on) gives every arc its own variance factor; Seed makes the probe-based redundancies reproducible. What a stream lets the estimator change is its Estimate setting on addStream ("law", "scale" or "none").

5.8 Step 8 — Add regularisation if the problem needs it

A free network needs a datum; a high-degree gravity field needs a Kaula rule. Both are declared as priors on named parameters:

task.addPrior("kaula", On="^[CS]", Sigma=1e-10, Estimate="scale");

See Priors and regularisation.

5.9 Step 9 — Read the report and act on it

R.report prints a verdict and the evidence behind it: the global test, flagged observations, the reliability, the whiteness of every stream. Each adverse verdict has a standard next step — snooping, a richer noise law, a functional model correction. See Reading the results and the report.

5.10 Step 10 — Take the results out

T = R.coefficients();                  % estimates, formal errors, confidence bounds
P = R.toTable(task);                   % every parameter by name, day and arc, with its estimate
save('run.mat', 'R');                  % R.meta records version, seeds and options

6 Declaring your problem

This chapter shows how to map a real problem onto a lsqvce.TaskDefinition. Every call is listed with its settings, their values, their defaults and the practice that works; the full reference of every class is in the API reference and in help lsqvce.<name>.

6.1 The picture

You describe one adjustment with four kinds of call: what is estimated for everybody (task.addCommon), which systems deliver data (task.addSystem, one per satellite, receiver or instrument group), what each system observes (sys.addStream, one per observation type) and what each system must estimate besides (sys.addLocal). Priors are declared where their parameters live (task.addPrior, sys.addPrior).

You write two kinds of function, and each has one fixed home:

function given to runs returns
Prepare(day, ctx) task.addSystem(name, Prepare=@p) once per system and day, before its streams anything; it reaches every Build of the day as ctx.Prepared
Build(day, ctx) sys.addStream(name, Build=@b, ...) once per stream and day ctx.newDay() filled with addArc

Everything else — reading the days in order, whitening every arc with its noise law, eliminating the local parameters, iterating the variance components — is done by the toolbox.

The design is block-arrow shaped: every arc sees the common parameters through its A and its own local parameters through its local design. The local blocks are eliminated arc by arc, so the memory need is set by the number of common parameters, not by the number of observations.

6.6 Arcs and schedules

The arcs Build adds are the arcs of the day. Without Arcs the toolbox takes them as they come, and days may differ in their number of arcs. Declare a schedule when "arc" locals must be counted before any data is read:

sys = task.addSystem("S", Arcs=4);                          % arcs 1..4 on every day
sys = task.addSystem("S", Arcs=@(day, stream) arcTable{day});   % a ragged schedule

With a schedule, ctx.ArcIds lists the day’s arcs; addArc fills them in order, Arc=id places one out of order, and a scheduled arc never added is a data gap. A day without any data in a system belongs off that system’s calendar (Days).

6.7 Multi-axis observations and their accuracy

A stream with several axes per epoch — a kinematic orbit, a gradiometer — declares Axes and returns its rows epoch-major (x₁ y₁ z₁ x₂ …). What the preprocessing knows about the accuracy of every epoch travels with the arc as Sigma:

out.addArc(A, l, t, Sigma=sigmaPerEpoch);                          % n x 1   scalar stream
out.addArc(A, l, t, Sigma=[sx sy sz]);                             % n x 3   per-axis sigmas
out.addArc(A, l, t, Sigma=permute(reshape(Q.', 3, 3, []), [3 1 2]));   % n x 3 x 3 covariance

The vector forms are standard deviations and the matrix form is a covariance — check one epoch by hand before a campaign. Sigma is relative to the law’s sigma: declare lsqvce.Noise.white(1) when Sigma already carries the absolute accuracy.

The range-rate between the two spacecraft depends on both orbits, so the pair is one system with three streams: the kinematic positions of each satellite and the inter-satellite range-rate. All three rest on the same orbit integration, which therefore goes into the system’s Prepare:

task = lsqvce.TaskDefinition(Days=59396:59426);
task.addCommon(shNames(60));                                   % SH coefficients to degree 60

6.9 Checklist before the first run

  • Every parameter has a name and the scope over which it is constant.
  • Every stream has its own Build; what several streams share is in the system’s Prepare.
  • Build adds one arc per addArc, with A (m × nc, addCommon order), l observed minus computed, t in seconds; nothing is whitened.
  • Local partials go by name (Local=), or as B with columns from ctx.cols — never by offset arithmetic.
  • Calling Build twice for the same day gives identical output.
  • Sigma, if given, matches the rows (epochs × axes = m).
  • disp(task) shows what you meant before the first fit.

7 Choosing the stochastic model

The weights of a least-squares solution are the inverse of the noise covariance. This chapter says what to declare, what to let the data estimate, and how to read the estimate back. The laws and their arguments are listed in the API reference (Noise laws) and in help lsqvce.Noise; the mathematics is in the theory.

7.1 Three facts, three places

fact declared in estimated?
the temporal law — how the errors of a stream correlate from epoch to epoch addStream(..., Noise=lsqvce.Noise.<law>(...)) yes, with Estimate = "noise", as the stream’s Estimate allows
the level of that law the law’s sigma (a standard deviation) yes
the per-epoch accuracy — what the preprocessing knows about each observation addArc(..., Sigma=) in Build never: it is data

The toolbox combines them per arc. A filter law (white, arma, an AR-whitened psd, var) is applied in batches of up to 20 000 rows that overlap by the memory of the filter (for an arma law with an MA part, until its impulse response has decayed to rounding), so the batching does not change the result. A dense law (acf, custom, a psd whitened as Toeplitz) is factorised over the whole arc: exact, at a cost of O(m³) and m² memory for an arc of m rows — for arcs of many thousand epochs prefer a filter law. Above 20 000 epochs a dense law is refused (lsqvce:covModel:denseArcTooLong, 3.2 GB for the factor alone at that length); MaxDenseArc= on the law raises the limit deliberately. Under Estimate = "noise" the estimator’s sweep forms every arc’s covariance densely whatever the whitener, so there the same limit applies to every law, a filter law included.

7.2 What to declare

law constructor use when cost per arc of m rows
white lsqvce.Noise.white(sigma) the colour is unknown (the default start), or truly white O(m)
ARMA filter lsqvce.Noise.arma(ar, sigma, MA=ma) a whitening filter is known O(m·p)
spectrum lsqvce.Noise.psd(f, S) a measured one-sided spectrum, f from 0 Hz O(m³) Toeplitz, O(m·p) with Noise.Whitener="ar"
correlation lsqvce.Noise.acf(@rho, sigma) the correlation is known as a function of the lag O(m³)
vector AR lsqvce.Noise.var(ar, Sigma) axes correlated in time across axes O(m·p·d²)
any lsqvce.Noise.custom(@covFcn) anything else O(m³)
stream’s Estimate under Estimate = "noise" use for
"law" (default; "scale" for a per-row sigma) shape and level estimated; the declared law gives only its sigma, as the starting level the colour is unknown
"scale" the declared shape kept, its level estimated a trusted spectrum or filter of uncertain level
"none" used exactly as declared a reference stream, a stream you trust completely
  • You do not know the colour of the noise. Declare lsqvce.Noise.white(sigma) with a realistic sigma and run Estimate = "noise": the estimator starts from white noise and finds the spectral shape. Under the stream’s Estimate = "law" (the default) this is what happens to every stream, whatever law it declares. (For an arma law sigma is an innovation standard deviation; as a level it is read as the marginal one.)
  • You know the noise spectrum. Declare lsqvce.Noise.psd(f, S) or an arma filter and set the stream’s Estimate = "scale" to keep the shape and estimate only the level, or "none" to use it as given.
  • Your axes are correlated in time across axes. Declare lsqvce.Noise.var (no per-arc Sigma). It is used as declared: Estimate = "noise" has no path for it and refuses it (lsqvce:fit:varUnderNoise).
  • A stream you trust completely — a prior stream, a reference — takes Estimate = "none" on its addStream.

7.3 Running the estimator

opts = lsqvce.Options(Estimate="noise", Pool="obsType", ArcFactors=true, ...
                      MaxPasses=7, Seed=1, Noise=struct('Grid', 120, 'Whitener', "ar"));
R = lsqvce.fit(task, opts);

Per pass the toolbox solves under the current laws, sweeps every arc once for its whitened residuals and their redundancies, and updates the spectral shape of every pool group, the level of every stream, the factor of every arc and the σ of every prior with Estimate = "scale". It stops when no component changes by more than Tolerance — the σ of a prior group included, which is first updated on the pass after it enters the solve, so the loop does not stop before — or after MaxPasses. A spectral bin the data barely determine may change by more, in proportion to its own standard error (chapter Reading the results and the report, “When the loop did not settle”).

The choices that matter:

choice guidance
Pool the default "stream" gives every stream its own shape. Streams of the same physics may share one ("obsType": both satellites’ range-rate), but measured on identical spectra that gains nothing for x. Never pool streams of different physics or units: positions with range-rate drives the normal matrix towards singularity, and a shared law biases both levels (poolNotWhite says so)
ArcFactors on when arcs are numerous and long enough to carry their own variance; off for few or short arcs
Noise.Grid the spectral resolution of the estimated law; finer grids resolve narrow spectral features but give each bin less redundancy per pass. Keep 60 with the default Smooth = 1. Fewer bins cut the estimator’s variance too, but bias the level low when the spectrum has a sharp low-frequency peak (16 bins: −12 % at AR(0.98))
Noise.Whitener how every psd law — the estimated one and any you declare — whitens an arc: "ar" for long arcs (cost O(m·p) instead of O(m³) in the solve); "toeplitz" (the default, exact) when the spectrum has narrow features a low-order filter cannot follow. Under Estimate = "noise" "ar" saves the solve only — the sweep forms each arc’s covariance densely (above) — and the estimated spectrum is then whitened by an AR(30) that approximates it: exact enough for short-memory noise (an AR(1) law to about 1 %), biased where AR(30) cannot follow the shape (a 1/f floor: tens of percent per bin, and the loop need not settle)
Probes, Seed the redundancies are estimated with random probes: 100 probes are the standard; a fixed Seed makes the run reproducible

Run one pass with Estimate = "none" first. If σ₀ is near 1 the declared weights are consistent. A σ₀ far from 1 says the Sigma scale is wrong — most often an information matrix used where a covariance was expected — and estimating a law on top will not fix it.

7.4 Reading the estimate

R.noise.stream           % the stream keys, in the order of model{}
R.noise.model{k}.sigma   % the estimated level of stream k
R.noise.Sgroups          % the estimated spectrum of each pool group
R.summary()              % one row per stream: level, whiteness
R.plot("psd")            % the spectra

The standard deviation of one arc is the product of three terms: the declared sigma, the square root of the arc factor, and R.sigma0. With sigma = 1 and a Sigma carrying the absolute accuracy, that product reads directly as how much too optimistic the preprocessing’s covariance was on this arc.

After convergence the whitened residuals of every stream should be white. The loop tests that in every pass, per stream, with a Ljung–Box test over 20 lags at α = 0.05; the result is in R.summary() and R.history.white (it is not a stop criterion). It detects short-lag correlation, periodic terms and excess low-frequency noise; a correlation that exists only at one long lag (an echo, a repeat-track pattern) is invisible to it — test for that with R.systematic('Lags', L).

Three assumptions of the model can be contradicted by the data, and the loop checks them after convergence (R.noise.checks, one warning each):

warning what the data say what to do
lsqvce:adjustVCEjoint:poolNotWhite a stream of a pool group is not white under the group’s shared law. Either the group mixes spectra, which biases both levels and the formal errors, or the stream has something unmodelled in it (an event, a drift) compare Pool = "stream"; regroup, or find the event
lsqvce:adjustVCEjoint:levelVaries a stream’s arcs scatter far beyond their sampling error around one level: the level changes from arc to arc or day to day arc factors for that stream
lsqvce:adjustVCEjoint:memoryVsArc the estimated correlation time exceeds half the median arc: the arcs’ local parameters absorb the long memory, and the level comes out low (−12 % at a correlation time of 200 against 256-epoch arcs) longer arcs, or a law that models the low frequencies

The formal errors of an estimated noise model are plug-in: R.sol.Cxx treats the estimated covariance as known. On short or few arcs they are 3–13 % optimistic in σ; on long records the optimism is negligible.

Arcs can be skipped in a pass: gap (no data) or nonPD (the arc’s covariance is not positive definite — a mis-scaled Sigma produces exactly this). A skipped arc keeps its previous factor; when more than Noise.SkipThreshold of a stream’s arcs are skipped, the pass is refused rather than estimated on a fraction of the data.

7.5 Outliers

Gross outliers belong to preprocessing. Inside the adjustment there are three tools:

  1. Arc factors down-weight a whole bad arc automatically (ArcFactors = true).
  2. Robust estimation down-weights single epochs: Robust = "igg3" or "bisquare" together with Estimate = "noise" weights every epoch of every stream inside the joint estimator, standardised by the stream’s own robust scale; a rejected epoch is removed from the arc exactly. The statistic is Baarda’s w for correlated observations — what deleting the epoch removes from v’Pv — tested one epoch at a time, the largest first (data snooping), and the truncation of the epochs that are kept is accounted for lag by lag. So the level, the law and σ0 of a robust run equal those of a plain run on clean data, on a coloured stream too (within 0.25 % in variance, measured), and a small blunder on a strongly correlated stream is found: at a lag-1 correlation of 0.98 a blunder of 2 standard deviations stands out by about 14 in w. Prefer a redescending function (igg3, bisquare) for gross blunders: Huber keeps part of their weight. The factors are in R.noise.robust.factor; a pass that rejects more than 45 % of the epochs warns that it has reached the breakdown point. A rejected set that flips back and forth between two passes is frozen at the union of the two (R.noise.robust.frozen names the pass).
  3. Diagnose, then decide. Read the outlier tests in R.report, repair or remove the observations in Build and run again. Weights taken from a robust run can be made data: zero the rejected epochs’ rows and mark them Excluded in the arc Build adds — the toolbox deletes such rows from a correlated law exactly, whole epochs or single axes (removing them leaves a gap that a psd or arma law, which counts lags in samples, takes for one step — lsqvce:covModel:unevenGrid says so); store the weights, never recompute them inside Build.

With Estimate = "none", Robust runs a stand-alone iteratively re-weighted solve on the whitened innovations, with its own budget RobustOpts.

8 Priors and regularisation

8.1 The idea

A prior says “these parameters are observed to be x₀, with standard deviation σ”. It is written as pseudo-observations L·x = x₀ + v on named parameters, and the toolbox treats it as data: it enters the normal equations, it has a redundancy (how much of it the data overrule), and its σ can be estimated like the level of any other stream. Regularisation is therefore never an option on the run: it is a declared part of the problem.

One call declares a prior group, on the object whose parameters it constrains: task.addPrior for common parameters, sys.addPrior for the local parameters of that system.

L q × nc (task) or q × nl (system), in the columns task.layout() announces — a datum (L = Nᵀ of the null space), degree-dependent weights, sums and differences

8.2 Typical priors

A datum for a free network. Minimum constraints on the null space N of the design (L = Nᵀ, value 0) fix the datum without distorting the solution. Declare the datum as a group of its own:

task.addPrior("datum", L=Nnull.', Sigma=1);

The solution and its covariance are the minimum-constraint ones for any σ, also when the datum is declared as several groups (for instance translation and rotation separately). The datum rows are constraints, not observations: the report does not count them as uncontrolled. Without a datum a rank-deficient system is refused by name; the toolbox never guesses one.

A Kaula rule on a gravity field. One group per rule, σ estimated:

task.addPrior("kaula", On="^[CS]", Sigma=1e-10, Estimate="scale");

On is a regular expression on the names given to addCommon; the toolbox builds one row per matched coefficient. Relative weights inside a group (degree-dependent Kaula factors) go into an explicit L instead: divide each row by its own relative σ.

Calibration parameters of an instrument. Priors on local parameters sit on the system:

grace.addPrior("accScale", On="^accScale", Value=1, Sigma=0.02, Estimate="scale");

The accelerometer scales of both satellites over a month form one group with many rows — exactly what makes their σ estimable. A group with one row cannot estimate its own σ.

8.3 Writing L yourself

task.layout() announces which column of A and of each system’s local design holds which parameter on which day and arc, with its name, so an operator can be built for any combination a pattern cannot express:

lay = task.layout();
c = find([lay.common.name] == "offset");             % the columns of a "day" common, one per day
L = [ones(1, numel(c)) / numel(c); diff(eye(numel(c)))];   % mean zero, smooth day to day
Lc = zeros(size(L, 1), lay.nc);  Lc(:, c) = L;
task.addPrior("offsetDatum", L=Lc, Sigma=1e-3);

lay.common(j) names the parameter of column j of A (.name, .row, .day); lay.systems(k).local(c) does the same for column c of system k (.name, .row, .day, .arc). examples/demo_priors.m builds priors both ways and shows that they agree.

8.4 Reading the result

R.noise.priors and R.noise.priorHistory report the σ of every common group per pass; a local group appears as the stream prior_<name> of its system in R.noise.model. λ = σ₀²/σ² is the regularisation the data support. R.report counts the redundancy of the prior rows like that of any observation.

A group with Estimate = "scale" is estimated only under Estimate = "noise" on the streaming kind. In any other run it keeps its declared σ, and fit says so once (lsqvce:fit:priorScaleHeld).

8.5 Activating a prior later

From = 3 activates a group in the third pass of an iterative run: the first passes then see the data alone. A single solve skips such a group with a warning.

What the numbers refer to.

  • Observations. An observation index is a row in sweep order: the arcs in the order they were accumulated, then the rows of a declared prior. Prior rows are counted in n and in the redundancy.
  • Units. On the streaming kind every row is whitened by its declared law before it is tested. v, w, r_i and the MDB therefore belong to whitened rows, and an MDB is in units of that row’s own sigma. For correlated data only sums such as sum(r_i) and vPv are the same in both frames.
  • Parameters. A parameter index in the report refers to the full parameter vector: the commons first (indices 1..numel(R.x)), then each system’s local parameters in block order. The u in the header counts both.
  • The a-priori sigma0. For whitened rows the a-priori sigma0 is 1. The report’s s0 is the a-posteriori value recomputed from the residual sweep and should match R.sigma0; Level 0 checks this.

9.6 Level 2 — LOCALISE (where is it broken?)

Level 2 locates individual bad observations by data snooping: one test per observation on its normalised residual

w_i = (P v)_i / (scale · sqrt((P Qvv P)_ii)).

The scale is the estimated s0 (Pope), the a-priori sigma0 (Baarda) or the robust MAD scale. With Bonferroni = true the level of each test is Alpha / n. The critical value follows the scale: Pope’s tau, the normal distribution, and for the MAD a Student t with r/2 degrees of freedom (calibrated to the nominal level; Pope’s tau there gave up to 60 times the nominal false alarms on small networks). The price of the valid level is power on short networks under heavy contamination: with 50 observations and 10 % blunders of 25 sigma, four or more of five are found in about 60 % of cases (snooping with Test="mad" does not change that); from about 200 observations all of them.

9.6.1 The contamination cross-check

Pope’s statistic divides by s0, and s0 is estimated from the same data that contain the blunders. A group of blunders therefore inflates the scale it is tested against, and the blunders mask each other. To catch this, the report compares s0 with a robust MAD scale of the raw standardised residuals and estimates the contaminated fraction fhat: the share of residuals beyond 2.5 robust sigmas. On clean data fhat sits near P(|Z| > 2.5) = 0.0124. As a backstop it also prints s0/sigma0, which contamination cannot suppress but which is only as good as your declared sigma0.

The null band is measured, for every n (the scored residuals): on clean data the count n·fhat is negative binomial with mean n · 0.0124 · (1 + 27/n) (a small sample’s MAD is biased low) and variance 1.69 times that mean. D.fhatTol is its 99.75 % point (false alarms ≤ 0.25 %), and fhat counts as collapsed only where it is implausibly low for clean data (P(K ≤ n·fhat) ≤ 1 %). Below n ≈ 450 even fhat = 0 is common on clean data (59 % at n = 30), so there a captured robust scale cannot be told from a sigma0 declared too small (D.collapseDetectable = false).

The cross-check appears whenever RobustCheck = true, whatever the Bonferroni setting. Exactly one of these lines is printed:

code severity condition action
SNOOP_SCALECHECK NOTE clean: fhat within its null band D.fhatTol s0 and the robust scale agree, so the flag list can be believed. (This line is omitted under Test = "mad".)
SNOOP_INDETERMINATE WARN fhat within its null band, s0/sigma0 > max(3, 2·(1 + 3/sqrt(2r))), and a collapse undetectable at this n Either sigma0 is declared too small (the common case: then the flag list can be believed) or more than half the data are bad and the robust scale is captured (then it cannot).   • SNOOP_MAD (NOTE) states that the robust scale replaced s0 (Test = "mad").

9.6.2 The snooping result

  • SNOOP_SETUP (NOTE) prints the test, Alpha, the corrected level, n, the critical value |w| > k and the number of false alarms expected by chance (Alpha under Bonferroni).
  • SNOOP_NOBONF (WARN) replaces it when Bonferroni = false. It prints the uncorrected level and roughly how many good observations will be flagged by chance. Set Bonferroni = true.
  • SNOOP_VACUOUS (ERROR, Pope only) appears when the critical value comes so close to the upper bound sqrt(r) of Pope’s statistic that a residual must carry at least 90 % of vPv to be flagged (k^2 / r >= 0.9, D.vacuityShare). Only a blunder that dominates the whole adjustment can then be found, and an empty list says nothing. Accept a weaker Alpha or a weaker family-wise correction, or accept that this network cannot detect its own blunders.
  • SNOOP_CLEAN (NOTE) means nothing exceeds the critical value. It prints the largest |w| and its observation index.
  • SNOOP_FLAGS (WARN) gives the number flagged, the number expected by chance, and so about how many are real. SNOOP_TABLE (NOTE) lists up to 15 of them, worst first, with columns obs, w, r_i, v, MDB. Read w and r_i together.
  • SNOOP_LOWR (WARN): some flagged observations have r_i < RWeak. A large residual on a weakly controlled observation may be error absorbed from a neighbour. Rejecting it is close to a coin flip; prefer to re-measure.
  • SNOOP_ITER (NOTE) prescribes the remedy. Reject one observation at a time (the largest |w|), re-solve and test again, because blunders mask each other and a single pass misses some of them:
[D2, REJ, sol2] = R.snoop();               % Pope, Bonferroni, one at a time
[D2, REJ, sol2] = R.snoop(Test="mad");     % under contamination
REJ.idx      % rejected, in order;  REJ.refused  % tripped but r_i < RMinReject (0.10)

R.snoop takes Test ("pope" or "mad"), Alpha and Bonferroni name-values; left out, they are R.diag’s, so Options.Diagnostics reaches them. It caps the number of rejections at max(10, 0.01·n) and stops at a fraction of 0.25 (MaxRejectFrac). It refuses to run at SNOOP_BREAKDOWN and SNOOP_REFUSE (Force = true proceeds with a warning), warns at SNOOP_INDETERMINATE (and at SNOOP_CONTAMINATED under Pope’s test), and tests only what R.diag tests (r_i > RMin). It refuses observations with r_i < RMinReject, re-solves cleanly over the survivors at the end, and leaves R unchanged. A prior’s rows, common or local, are never rejected, and the re-solve keeps the prior as a prior (a datum stays a datum); the re-diagnosis keeps R.diag’s thresholds and storage (Store, NWorst, RobustCheck). The returned D2 counts in the original observation numbers (D2.flagIdx, D2.rejectedIdx, …); its per-observation vectors cover the survivors, and D2.obsIdx names their original numbers. It cannot reject single rows of a correlated batch (lsqvce:snoop:correlatedBatch): there, remove the epoch in Build or use Robust.

9.7 Level 3 — RELIABILITY (what can you not check?)

Level 3 shows which observations the tests could not check at all.

  • REL_HEAD (NOTE) prints the smallest redundancy number and its observation, the mean redundancy r/n, and the MDB non-centrality delta0. delta0 is computed at the Bonferroni-corrected level and Beta: 4.13 at a level of 1e-3 with Beta = 0.2, and larger as n grows. It is the normal (Baarda, known-sigma) value. Under Test = "mad" the threshold is Student t with r/2 degrees of freedom, so the bias that can hide from that test is larger (about +50 % at n = 30, +25 % at n = 50, +6 % at n = 200); the line then says that the MDB, the envelope and the external reliability are the Baarda values.
  • REL_QUADRANTS (NOTE) counts the observations in each cell of the (|w|, r) table. |w| is high when it exceeds the critical value; r is low when it is below RWeak.
quadrant |w| r meaning
clean outlier high high reject with confidence
AMBIGUOUS high low could be a neighbour’s error; re-measure
verified low high tested, and passed
UNTESTED low low not “fine”: the test had no power

A residual shows only the fraction r_i of an error in its observation. A small |w| on a low-r observation is therefore no evidence of health. R.reliability() gives the same quadrant per observation; the rows of a datum prior carry the label "datum" and are not counted in any quadrant.

code severity condition action
REL_SILENT WARN observations in the UNTESTED quadrant These observations did not pass the test; the test could not see them. Strengthen the geometry (more or better-placed observations), or validate them externally.
REL_AMBIGUOUS WARN flagged observations with r_i < RWeak Re-measure rather than reject.
REL_ENVELOPE NOTE always, when MDBs are finite The hidden-blunder envelope: the median, 90th and 99th percentile and the worst MDB, in units of each observation’s sigma. “Half of my observations could hide an undetected error larger than the median.” The percentiles come from a fixed-seed reservoir of 5000 samples.
REL_MDBINF ERROR observations with infinite MDB No error in these observations, however large, can be detected. They drop out of the percentiles above, so the envelope looks better than it is.
REL_UNCONTROLLED ERROR observations with r_i ≤ RMin Their residual is forced to zero, so a blunder in them passes into the parameters unseen. The first indices are listed. Add observations that constrain the same parameters, or remove the parameter that only those observations determine.
REL_WEAK WARN RMin < r_i < RWeak A blunder in these is only partly visible. Data snooping has little power here.
REL_GOOD NOTE none weak, none uncontrolled Snooping has power everywhere.

External reliability (REL_EXTERNAL) answers one question: how far could the worst undetectable blunder (one MDB in the worst observation) move a parameter, in units of that parameter’s own sigma? The report names the observation and the parameter. Under a healthy geometry this number shrinks like 1/sqrt(n), so it is judged against the value expected for a network of this size, 4.0 · delta0 / sqrt(n):

ratio to expected severity action
≤ 1.8 NOTE Normal for this size.
1.8 – 3 WARN The geometry is weaker than it should be.
> 3 ERROR One observation carries far more leverage than the rest. Find it through the minimum r_i and the named observation, and do not trust the formal sigmas.

If the absolute value exceeds one sigma, the line adds that an undetectable blunder could move the parameter by more than its stated precision. When that happens at a normal ratio, the remedy is more observations, not a different estimator.

9.8 Level 4 — PARAMETERS (what do you actually know?)

Level 4 checks conditioning and correlations, and lists the parameter precisions.

  • PAR_COND (NOTE) prints cond(R) and cond(N). On the fit path these are lower bounds formed from the blocks of the cofactor (no SVD), and they are marked [LOWER BOUND]. The true conditioning can be worse than printed, never better, so the thresholds below are optimistic.
  • PAR_ILLCOND: WARN when cond(N) > 1e10, with roughly log10(cond(N)) of 16 digits lost. ERROR when cond(N) > 1e14: the printed sigmas are meaningless. Rescale the parameters so that the columns of the design have comparable norms, and use Backend = "qr", which avoids squaring the condition number. A rank defect (a free network) needs a datum, which you declare as a prior (chapter Priors and regularisation).
  • PAR_CORR reports the strongest correlation and its parameter pair. It is a NOTE at most 0.95, a WARN above 0.95 (nearly inseparable: use R.ellipse(i, j) rather than the individual sigmas), and an ERROR above 0.999. In the ERROR case only a combination of the two parameters is determined. Fix one of them, reparameterise to estimate the combination, or add observations that separate them.
  • PAR_TABLE (NOTE) lists the first 30 parameters of the full vector: x, the a-priori sigma (sigma0 · sqrt(Qxx_jj)) and the scaled sigma (s0 · sqrt(Qxx_jj)). The scaled column is what R.coefficients reports for the commons.
  • PAR_SCALE (WARN) appears when |s0²/sigma0² − 1| > 0.1, so that the two columns differ. Which column is honest depends on why the variance factor deviates. If the weights were wrong, the scaled column is right. If there are outliers or systematics, neither is right. Resolve Levels 1 and 2 before quoting either.

9.9 Beyond the report: the stochastic model

The report judges one solve under the final weights. Whether those weights describe the noise, stream by stream, is a separate question, and the report does not answer it. For an Estimate = "noise" run, read it from R.history, R.summary() and R.convergence().

9.9.1 Whiteness per stream

On every pass the loop tests the law-whitened residuals of each stream with a Ljung–Box test. The test pools over the stream’s arcs, uses K = 20 lags and calls a stream white when p > 0.05.

T = R.summary();             % stream | sigma | arOrder | white | pValue  (final pass)
T(~T.white, :)               % the streams that never whitened
R.history.streams            % stream keys 'satKey|obsType', the column order of
R.history.white(end, :)      %   these per-pass matrices (nPass x nStream)
R.history.whitePval(end, :)

In summary(), sigma is the stream’s level factor sqrt(mean arc factor). It is near 1 when the declared sigma was right, and it tells you by how much the declared sigma was off. arOrder is NaN, because the joint estimator fits a spectrum, not an AR order.

A stream that is not white has residual correlation that its law does not describe. Possible causes and remedies, roughly in order:

  1. The law was not estimated for it. If the stream’s covariance spec has estimate = "none" or "scale", the declared law is used unchanged (its R.noise.model{k}.C is then empty). Set estimate = "law" for that stream.
  2. It shares a law with streams that behave differently. Use a finer Pool ("obsType", or "stream" for one law per stream).
  3. The spectral grid is too coarse for its correlation: raise Noise.Grid.
  4. The functional model is incomplete. An unmodelled signal (a drift, a once-per-revolution term) appears as coloured noise. Run R.systematic(Covariates=struct('time', t, ...)): the binned-mean test points to the covariate. A correlation that lives only at a long lag (an echo, a repeat pattern) is invisible at K = 20; test it with R.systematic(Lags=L).

R.plot("psd") draws the estimated spectral shape of each pool group, and R.plot("residuals", Stream="...") draws a stream’s whitened residuals against time.

9.9.2 When the loop did not settle

The loop stops when two conditions hold. Every arc factor changed by at most Tolerance. Every spectral bin j changed by at most Tolerance·max(1, sqrt(200/r_j)), where r_j is the bin’s redundancy and sqrt(2/r_j) the relative standard error of its estimate. A bin with a redundancy of 200 or more is held to Tolerance. A bin with less, such as the zero-frequency bin that per-arc parameters absorb, may move further, in proportion to its own standard error: at the default Tolerance 1e-2, by a tenth of it. A finer step would ask for more precision than its estimate has. A smaller Tolerance tightens every bin. (Before 6.26.0 every bin was held to Tolerance. On the fixtures of the development record that took 14–168 passes, while the solution was already within 0.1–0.2 of its standard error of the end point after 10.)

Each pass records R.history.binRatio (the largest change of a bin divided by its bound, so ≤ 1 means every bin settled), R.history.levelDev, R.history.maxDev (the largest |α² − 1|, a reading) and R.history.xStep (the largest change of the solution since the pass before, in units of its own standard error). R.convergence() gives one row per pass with pass, maxSigmaOffset (the largest |sigma − 1| of the per-stream level factors: a reading, not the stop rule), nWhite, minWhitePval, converged, maxDev, levelDev, binRatio and xStep. R.convergence(Plot=true) and R.plot("convergence") draw the same record.

With stopReason = "maxPasses", the warning names the bins that still move, with their redundancy against the median of their group, and the solution’s last step:

  • If xStep is a few hundredths or less, the solution has settled to well within its errors, and the bins that still move are ones the data barely determine.
  • If binRatio is still falling, the loop needs more passes: raise MaxPasses.
  • If it oscillates, there is too little redundancy per component: coarsen Pool ("obsType" or "all"), use a smaller Noise.Grid, or smooth the spectrum (Noise.Smooth). A spectrum that keeps moving also points to too few arcs per frequency, or a start far from the data.
  • If one stream stays non-white on every pass, see “Whiteness per stream” above.

9.9.3 Skipped arcs and the warnings inventory

An arc that cannot be used in a pass is skipped and keeps its previous factor. The reason is 'gap' or 'nonPD' (its covariance could not be factored). R.history.skips lists every skip as {pass, arcKey, reason}. A pass that skips more than Noise.SkipThreshold (0.2) of one stream’s arcs is refused with lsqvce:adjustVCEjoint:skipThreshold. A few nonPD skips usually mean a Cep or a law that is not positive definite on those arcs, so inspect what that day’s Build adds.

Warnings are raised once per run. Muted or not, every warning identifier the run raised is listed in R.meta.warnings (first-fired order). Check it in batch jobs. The ones that qualify a result:

9.9.4 Robust runs

A robust run reports ROBUST_FIT at Level 1. Its weights come back in R.noise.robust when the robust pass runs inside the noise loop: influence, scale per stream, factor per epoch in sweep order, keys, truncation (the factor the hard σ0 is corrected by) and frozen (the pass a cycling rejected set was frozen at, 0 if none). How to read it, in order:

  1. Level 0. Check that [identity holds] is printed and that no [ERROR] appears. If one does, stop: the verdict is INVALID.
  2. Level 1, loop line. If the run iterated, check that the stochastic model settled. If not, every later line is provisional.
  3. Level 1, the ratio. Read the confidence interval on sigma0, not the pass/fail. A ratio well above 1 sends you to Level 2 (outliers) and to R.systematic.
  4. Level 2. Read the scale cross-check before the flag list: if the check reports contamination, the list is not to be believed. With flags, read each w next to its r_i, and reject with R.snoop, one observation at a time.
  5. Level 3. Check that the quadrant table has no UNTESTED or AMBIGUOUS counts and that no uncontrolled or infinite-MDB observations are reported. Check that the external reliability is normal for this n.
  6. Level 4. Check that the conditioning is far from 1e10 and that no correlation is above 0.95. If PAR_SCALE fires, decide which sigma column applies only after Levels 1 and 2 are resolved.
  7. Outside the report. For a noise run, check R.summary() for non-white streams, R.history.skips, and R.meta.warnings.

Then quote the result: R.coefficients() for the commons, R.toTable(task) for every parameter in your own table layout, and R.meta for the provenance.

11.6 demo_workflow: build your own case

Purpose. This is the from-scratch recipe for wiring your own data into a lsqvce.TaskDefinition, choosing what to estimate, and reading the result in the right order.

Run. demo_workflow is a script with no arguments and no outputs. It runs clear; clc; close all. The help text recommends running it section by section (Ctrl+Enter).

Outline and logic. The script is organised as Sections 0 to 5:

  • Section 0 lists the three ways to make a task:
    • in memory: lsqvce.TaskDefinition.fromMatrices(A, l, Weights=p);
    • batched: lsqvce.TaskDefinition.fromBatches(@batchFcn, NumBatches=K, NumUnknowns=u), or X0=x0 for the nonlinear form;
    • streaming: lsqvce.TaskDefinition(Days=days), filled with addCommon, addSystem (its Prepare), addLocal and addStream (its Build and Noise).
    It also states the batched callback contract [A, l, p] = batchFcn(k), with p the weights 1./sigma.^2. The callback is called twice per batch and must return identical data both times.
  • Section 1 synthesises 3000 observations with 8 unknowns and cuts them into 30 batches with a closure over precomputed batch edges. It sanity-checks batchFcn(1) with an assert and makes task = lsqvce.TaskDefinition.fromBatches(batchFcn, NumBatches=nb, NumUnknowns=u).
  • Section 2 is a decision tree in comments: which kind, and when to use Estimate="noise". It then runs R = lsqvce.fit(task) with default options.
  • Section 2b reads the verdict in a fixed order:
    1. integrity, R.diag.sumRRelErr;
    2. variance, R.diag.varRatio;
    3. blunders, R.diag.nFlag;
    4. reliability.
    The one-line verdict comes from R.report('Verbose', false).verdict.

11.7 demo_fit: the three data kinds, one call each

Purpose. This example shows every kind of task that lsqvce.fit accepts, end to end on the user tier: lsqvce.fit, lsqvce.Options, lsqvce.Results and R.report. It also shows robust estimation, a datum declared as a prior, Gauss–Newton through X0, and watching a run with OnPass.

11.10 demo_priors: regularisation in the announced layout

For the full reference, see the chapter Priors and regularisation.

Run.

[R, s] = demo_priors();

R is the regularised solve. s holds:

  • .nullDim;
  • .unregularised: the error identifier;
  • .sigma0 and .zSignal;
  • .nPseudo, .formGap, .datumGap and .priorLevel.

The case. The data have four harmonic signal coefficients ('common') and one offset per day (task.addCommon("offset", Scope="day")). 11.12 demo_sensors: system / sensor / day, gaps, and a bad day

Purpose. This example declares the full hierarchy:

  • a system is one task.addSystem;
  • a sensor is one stream of its system, sys.addStream;
  • a day is an entry of the task’s Days.

It shows a data gap, finds a bad day through one variance factor per sensor-day, and then estimates the per-sensor noise levels without that day. The order is the point: a variance component is an average over its stream, so an event inside the stream corrupts the level.

Run. demo_sensors() takes no arguments and returns nothing.

The case. There are six common unknowns and two systems:

  • GRACE-C (id 'C') carries KBR, LRI and GPS and has 4 locals;
  • GRACE-D (id 'D') carries KBR and LRI and has 3 locals.

The data cover 10 days with 60 observations per sensor and day. The true sigmas are KBR 1.0, LRI 0.4 and GPS 2.5, but every sensor is declared with sigma 1. GRACE-D’s LRI is missing on days 4–5, and GRACE-C’s KBR carries a 6-sigma offset on day 7.

Logic.

  1. Generate the data into a containers.Map per system.
  2. Declare the task. Each system’s Arcs is a resolver from makeSchedule that returns no arcs on an outage day, which is how a data gap is declared. Every sensor is a stream with Noise=lsqvce.Noise.white(1), the claim.
  3. Solve once with Options(Verbose=false) and print R.sigma0 (the symptom).
  4. Find the bad day. Run Options(Estimate="noise", Pool="obsType", ArcFactors=true, MaxPasses=20, Noise=struct('Grid', 8)). Every arc, here one system, sensor and day, gets its own variance factor. The demo looks each factor up by lsqvce.util.arcKey in R.noise.arcKeys and prints it divided by the median of its stream, because the factors are absolute against the claimed sigma 1. An arc above 5 times its stream’s median is marked <<< EVENT.
  5. Remove each event’s arc from the store, so the arc resolver returns no arc for it, as for an outage. Then run Options(Estimate="noise", Pool="obsType", ArcFactors=false, Noise=struct('Grid', 8)). The KBR streams of both systems share one spectral shape, and every stream keeps its own level. The demo prints R.summary().sigma per stream against its truth.

Noise.Grid 8 is used because an arc holds only 60 samples. With the default 60-bin law, the bins that the data barely determine decay toward zero, and the loop needed 168 passes. The help block records the measured values: the event is 15.9 times its stream’s median, every other sensor-day lies between 0.5 and 1.8, and the levels come back within 4.0 % of the truth. Estimated with the event still in the data, C|KBR came back 46 % high.

Outputs. [task, kit] = kbr_variational(cfg). The task has:

  • the commons C_n_m and S_n_m, each with its unit (1e-10) as Info;
  • the calendar cfg.days;
  • one system "GRACE-FO" (Id=1) with:
    • "arc" locals: initial position and velocity per satellite (C_x0, …), and the KBR bias, drift and once-per-revolution cos/sin terms;
    • "day" locals: accelerometer bias and scale per satellite;
    • the arc schedule (cfg.arcsPerDay or cfg.arcs), the Prepare prepareKbrDay, and one stream per entry of cfg.obsTypes, each with the Build buildKbrDay.

Every parameter carries a declared unit as Info, so the physical value is unit .* estimate. Position streams carry their sigmas in each arc’s Sigma.

kit exposes the physics as function handles:

  • unitCommon and unitLocal;
  • coeffIndex, harmonics, makeField and fieldEval;
  • propagate and accModel;
  • eraRotation, readGfc, readL1B, prepareDay and buildDay.

prepareKbrDay, the system’s Prepare, integrates every arc of the day once each time the day is built and forms the rows of every stream, taking the columns of each arc’s locals from ctx.cols(names, Arc=id) (helper arcColumns); buildKbrDay picks its stream out of ctx.Prepared and adds each arc with Arc=id. Only the current day’s integration is kept; CacheDays keeps the built rows. kit.prepareDay and kit.buildDay take (day, ctx), so only the toolbox calls them.

Limitations. The help lists these:

  • kit.eraRotation is a stand-in for synthetic data only.
  • L1B layouts and frame conventions must be checked against the product handbook.
  • Forces other than the static field and the accelerometer enter only through background.
  • KBR quality flags are not screened.
  • Memory per stream is 8 m nc bytes per day, about 0.5 GB for KBR at 5 s and degree 60.

Errors carry kbrvar: identifiers, for example kbrvar:badConfig, kbrvar:noFile, kbrvar:accGap and kbrvar:emptyArc.

11.17 template/lsqvce_template.m: the engine-tier starting point

Purpose. This template declares a lsqvce.TaskDefinition from a procOpt configuration struct and builds from it the cell array of Loader objects that the engine-tier functions take (lsqvce.engine.adjustBlock, lsqvce.engine.adjustRobust). Use it when your pipeline is driven by procOpt and you want the Loader objects in hand. On the user path you do not need them: lsqvce.fit(task) runs the task.

Run. Copy the file, rename it, and write the stub myBuild:

[L, task] = myCase(procOpt);
R = lsqvce.engine.adjustBlock(L, procOpt.days);
R.report();

Structure.

  • declareTask is real code. It makes one task.addSystem per entry of procOpt.observationGroups, with its "day" / "arc" / "system" locals and one addStream per observation type, each with a white, unit a-priori Noise (aprioriNoise) and the Build myBuild. The tables of procOpt carry the scope in column 1 and a unique name in column 2.
  • The Loaders come from lsqvce.engine.declaration(task.declaration()), the step fit uses.
  • myBuild(day, ctx) is a stub. It raises lsqvce_template:notImplemented until you replace it. It must be deterministic and add the day’s arcs with out.addArc(A, l, t, ...), the per-epoch accuracy as Sigma, with multi-axis rows in epoch-major order.
  • A procOpt without observationGroups or days raises lsqvce_template:badProcOpt.

11.18 demo_messaging: what each verbosity level prints

Purpose. This example lets you compare the verbosity levels on real output before you adopt a level for long runs. See also the chapter Watching a run.

Run.

demo_messaging()                          % levels [0 1 2]
demo_messaging('levels', [0 1])
demo_messaging('toFile', '/tmp/levels.txt')

There are no outputs; everything is printed. A file that cannot be opened raises demo_messaging:badFile.

Logic. For each level, runAtLevel redirects the toolbox log with lsqvce.util.log.set('fid', fid, 'screen', false) and builds demo_grace_dataLoader(). It runs Options(Estimate="noise", Pool="stream", ArcFactors=false, Verbose=lvl, MaxPasses=1), then reads the captured text and prints it under a header. The header gives the level and lsqvce.util.verbosity.describe(lvl).

What you will see.

  • Level 0 prints nothing but warnings. Warnings are not controlled by the verbosity level, and a single pass does not converge.
  • Level 1 prints the stage label for each swept system and a convergence line for each pass.
  • Level 2 prints the same as level 1 when you go through lsqvce.fit. The help block explains why.

The per-stream view is not printed. Read it afterwards with R.summary() or R.convergence('Plot', true).

11.19 bench_qr_vs_normal: which backend, measured on your machine

Purpose. This benchmark measures the cost of Backend="qr" against Backend="normal" on your hardware, and shows when the accuracy of QR is needed.

Run.

bench_qr_vs_normal()                                       % u = [10 30 50 100], n = 1e5, nk = 5000, reps = 3
bench_qr_vs_normal('u', [10 50 100], 'n', 2e5, 'nk', 5000)

There are no outputs; the benchmark prints two tables.

Logic. Both runs use the same batched task, lsqvce.TaskDefinition.fromBatches(src, NumBatches=nb, NumUnknowns=u), with Options(Backend="normal") and Options(Backend="qr").

  1. Timing. For each u, the benchmark times both runs, keeping the best of reps repetitions. It prints the times, their ratio, and the relative agreement of R.x. The timed call is the whole fit, including diagnostics, so the difference between the two times is the cost of the backend.
  2. Accuracy against conditioning. With u = 10 and n = 20000, the benchmark makes column 2 nearly collinear with column 1, for eps = 1e-1 … 1e-8. It compares both backends with an SVD reference and prints cond(R.sol.Cxx), which equals cond(N), the two errors, and a verdict. When N is singular in double precision, the normal path refuses with lsqvce:normalEq:notSPD. The benchmark catches that refusal and reports QR as mandatory.

The recipe the benchmark prints: solve once with "normal", read cond(R.sol.Cxx), and switch to "qr" only when that number calls for it. For the backend option itself, see the chapter lsqvce.Options of the API reference.

12 Large problems

A GRACE-FO month at degree 60 has millions of observations, about 3700 common and tens of thousands of local parameters. This chapter lists the settings that decide whether such a run fits in time and memory. The defaults are safe; change them when you have measured.

12.1 Memory

The accumulator holds the reduced common system, nc × nc. Local parameters are eliminated arc by arc and never enter it. The largest transient object is one built day: m × nc doubles per observation type — at degree 60 about 190 MB for a six-hour three-axis arc.

CacheDays (default 1) is the number of built days kept resident per system. An iterative run reads every day twice per pass; CacheDays = Inf builds each day once per run if the calendar fits in memory. A system’s Prepare result is kept for the current day only, whatever CacheDays: it adds one day’s worth, and runs again whenever a day is rebuilt. If reading the raw files is the expensive part, cache those inside your Build closure instead.

12.2 Time

setting effect
Noise.Whitener = "ar" whitens a long arc in O(m·p) instead of the O(m³) of the dense Toeplitz factor, which is formed over the whole arc (m² memory, refused above maxDenseArc = 20 000 epochs); check the AR fit once with lsqvce.engine.checkPSD. It speeds up the SOLVE: under Estimate = "noise" the estimator’s sweep still forms every arc’s covariance densely (m² memory, O(m³) per arc and pass), and the same maxDenseArc refuses a longer arc there — cut long arcs, or estimate the law on a subset and solve the whole with Estimate = "none"
Probes the cost of the redundancy sweep grows linearly with it; 100 is the standard, fewer gives noisier redundancies
Parallel = struct('Mode', "parfor", 'DistributeDays', true) distributes the day loop of the accumulation over workers; the result is bitwise identical to the serial run
MaxPasses, Tolerance the number of passes of an iterative run

12.3 Resampling days

A bootstrap over days refits the problem once per replicate, and each refit re-reads and re-eliminates days the first fit already reduced. R.contributions() keeps every day’s reduced contribution (one more pass over the data), and lsqvce.solveContributions(C, c) solves a replicate from them in O(D·nc²): c says how often the replicate drew each day. The days keep the run’s final weights; the noise model and robust weights are not re-estimated per replicate. Declare day-specific unknowns per day or per arc: a local that spans days couples them, and the days then have no separate contributions.

12.4 Backend

Backend = "qr" (default) keeps the square-root information form and is the safer choice on ill-conditioned common blocks; "normal" forms the normal equations and is faster on well-conditioned ones. Both give the same numbers to rounding where both work. examples/bench_qr_vs_normal.m measures the trade-off on your machine.

12.5 Before a long run

  1. Run one day with Estimate = "none" and read the report.
  2. Run a few days with Estimate = "noise" and MaxPasses = 3 and look at R.plot("psd") and R.summary().
  3. Fix Seed so the long run is reproducible, and save R with its meta.
